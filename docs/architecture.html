Aerospace Analyst Copilot — architecture reference

Target state (W16). Three views: system components · one query end to end · inside the agent loop. Living document — update alongside DECISIONS.md when the architecture changes.

1 · System architecture

Every component and how they connect. Purple = application layer, teal = data & retrieval, coral = models, gray = infrastructure.

Live request path (top half). The user talks to the Chainlit UI, which calls the stateless FastAPI service. Every request gets a request_id at the door, then passes admission control (concurrency caps with a degrade ladder — ADR-0010) before any model work. The query pipeline holds the three working parts: the agent/fast-path decides how to answer, retrieval finds evidence in Postgres full-text search and Qdrant vectors (merged by RRF, sharpened by a reranker), and the LiteLLM gateway is the only door to any model — routing, fallbacks, and the paid-tier rescue all live there, which is why swapping models is a config change.

Data path (bottom half). Ingestion runs on schedules, independent of user traffic: three workers pull EDGAR filings, NTSB records, and Launch Library 2 data into Postgres (the source of truth, including each record's public source URL), and embeddings flow onward to Qdrant. If an index is ever wrong, it can be rebuilt from Postgres.

Everything is watched and gated. Observability taps every layer — Langfuse traces each LLM call, Prometheus/Grafana track cost, latency, and quality with alerts. Code reaches Railway only through GitHub Actions, where tests and the eval gate must pass first.

2 · One query, end to end

What happens between a question being typed and its answer being logged.

Two early exits keep costs down. A query that fails the scope check (off-domain, abusive) or hits the cache never touches a model — instant response, near-zero cost. Only genuine, new questions continue.

The classifier picks the cheapest sufficient route. Simple lookups ("when is the next Falcon 9 launch?") take the fast path: one retrieval, one synthesis call. Multi-source or multi-hop questions ("do this company's stated risk factors match its incident record?") enter the agent loop, which plans, calls tools, and judges its own evidence — never exceeding two replans.

Both routes face the same quality gate. Every answer's claims are checked against the exact chunks they cite; a grounding failure on the free model tier earns exactly one retry on a paid model, and the rescue rate is tracked. The final response carries citations that link to the original public source, a confidence score, and a disclaimer when the answer resembles investment advice. Every query — success or failure — ends as a full trace, metric datapoints, and an optional user rating, so any answer can be debugged after the fact without rerunning it.

3 · Inside the agent loop

The multi-hop path from diagram 2, opened up. The design goal: every exit is deliberate.

The loop is a bounded state machine, not a while-loop. The planner reads the question and emits structured tool calls. Before anything runs, the budget check enforces four hard caps — steps, dollars, wall-clock time, and (during a deploy) the drain deadline (the one everyone forgets: a hung external API can freeze a loop whose step and token counters look fine). Any cap tripping routes to synthesis with whatever evidence exists — an honest partial answer, never a hang or an error page.

Tools run in parallel, and failure is data. Independent calls execute concurrently with per-call timeouts; a failed tool becomes a recorded result ("EDGAR search timed out") the model can reason about, instead of crashing the batch. A dead-loop check hashes each normalized tool call — the model re-asking the same question is force-terminated.

The judge is the stopping brain. A cheap model must map each sub-question of the query to specific evidence items; unmapped sub-questions become the gaps. If not, the identified gaps feed a replan — capped at two, because "one more hop will fix it" is how agents run forever. Successful hops thread forward: entities extracted from hop one become precise queries in hop two.

Every exit is named. The run ends with a logged termination_reason — answered, budget, dead_loop, or error — and the distribution of that one field is the single best health metric for the whole agent.
